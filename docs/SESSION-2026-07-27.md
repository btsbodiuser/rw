# Dev Session — 2026-07-27

Planning session (no code changes). Discussed pivoting the site from a general Korean-brand reseller into a **running & trail running specialty store**, reusing the existing PHP backend/API layer as-is while the frontend gets fully redesigned/rebuilt separately. Ended with a phased plan and two open decisions to confirm before implementation starts.

---

## Context: current state vs. target

Reviewed `docs/SYSTEM-OVERVIEW.md`, `docs/INTRODUCTION.md`, `docs/todolist.md`, and the full schema in `docs/rw.sql` (40+ tables) against runnersneed.com as a reference for what a running specialty retailer looks like.

**Finding:** the backend is solid and mostly reusable, but the *product data* is currently generic (Nike/Puma/Zara sneakers, clothing, supplements) rather than running-specific. The "Runners World" branding isn't yet backed by running-specific taxonomy or technical product data.

**Already in place and reusable as-is:**
- `activity_types` table (Trail Running, Road Running, Hiking, Cross Training, Walking, Gym) + `product_activity_types` junction — right taxonomy shape, just underused (6 of ~50 products tagged).
- `product_sizes`, `product_colors`, `product_variants` — variant infrastructure.
- `product_price_tiers` — bulk pricing.
- `blog_posts`, `testimonials`, `sliders`, `faqs`, `newsletter_subscribers` — content infrastructure.
- Full order/cargo/delivery/QPay pipeline — no changes needed for the pivot itself.

**Gaps identified vs. runnersneed.com:**
1. No real product reviews table (`products.rating`/`reviews` are manually-set aggregate numbers, not customer-submitted).
2. No wishlist/favorites.
3. No "Shoe Finder" / gait-and-goal quiz.
4. No running-specific technical specs on products (drop, stack height, cushioning, stability, plate, weight).
5. No loyalty/rewards program.
6. No coupon/discount-code system or gift cards.
7. No physical-store/run-club layer (`shops` = brand/seller entities, not community/event locations).
8. Blog likely not tied to buying-guide content marketing.

---

## Decisions made

- Keep backend + APIs; frontend will be fully rebuilt separately (not part of this plan).
- Site direction: **running and trail running store**, confirmed.
- **Club feature required** — both free (open community events) and paid (membership perks) tiers.
- Club activity scope: scheduled group runs/events, race/challenge results + leaderboard, community feed/posts. (Coach/pace-group structuring discussed as an option, not committed.)
- Launch priority: **Phase 1 (running specs) + Phase 3 (shoe finder)** first — the core retail differentiator — with Club (Phase 5) proceeding in parallel as an independent schema track since it doesn't block or get blocked by the catalog work.

---

## Phased plan

1. **Phase 0 — Re-taxonomy** (data only, no schema change): recategorize `categories`/`shops` around running (Road Running Shoes, Trail Running Shoes, Racing/Carbon Plate, Apparel, Nutrition/Hydration, GPS Watches, Accessories); expand `activity_types`; tag products properly.

2. **Phase 1 — Running-specific product data** *(priority)*: new `product_running_specs` table — terrain (road/trail/hybrid), drop_mm, stack_height_heel/forefoot_mm, weight_g, cushioning (minimal/balanced/max), stability (neutral/stability), plate (carbon/none), best_for (daily_trainer/race/recovery/tempo/trail_technical), lug_depth_mm (trail only). One row per product.

3. **Phase 3 — Shoe Finder** *(priority)*: quiz (terrain, distance, foot strike/pronation, cushioning preference) scoring products via Phase 1's spec fields. Mostly an API endpoint (`/api/shoe-finder.php`); depends on Phase 1.

4. **Phase 5 — Club** *(parallel track)*: draft schema —
   - `clubs` (id, name, slug, description, cover_image, is_active) — start with one row, kept as a table for future multi-chapter support.
   - `club_memberships` (customer_id, club_id, tier: free/paid, status, started_at, expires_at, payment_ref).
   - `club_events` (club_id, title, description, event_type: group_run/race/challenge/social, start_at, location_name, district_id, distance_km, pace_group, capacity, members_only).
   - `club_event_rsvps` (event_id, customer_id, status: going/waitlist/cancelled, checked_in).
   - `club_results` (event_id nullable, customer_id, distance_km, duration_seconds, proof_image_id, verified) — powers leaderboard.
   - `club_posts` (club_id, author_admin_id/author_customer_id, content, image_ids, event_id nullable, likes_count).

5. **Phase 2 — Reviews + Wishlist**: `product_reviews` (customer_id, product_id, order_item_id for verified-purchase, rating, text, photos, status) with admin moderation; `wishlists` (customer_id, product_id). Independent, low risk.

6. **Phase 4 — Promotions** *(most deferrable)*: `coupons` (code, type %/flat, min order, expiry, usage limits), optionally `gift_cards`, optionally a points/loyalty ledger tied to `orders`.

---

## Open questions (unresolved — need answers before building Phase 5)

1. **Paid club membership billing** — current QPay integration is one-shot QR payment, not recurring subscription billing. Two options:
   - (a) Manual renewal — one-time QPay charge per period, membership expires and prompts renewal, no auto-billing. *(recommended default — matches existing payment flow, much less work)*
   - (b) Real recurring billing — bigger lift, and QPay's Mongolia merchant API may not cleanly support it.

2. **Leaderboard verification** — how are `club_results` entries trusted?
   - Self-reported (member types distance/time or uploads a screenshot as `proof_image`). *(recommended default for v1 — a day's work)*
   - Real GPS integration (Strava/Garmin OAuth import) — a separate project on its own (OAuth, webhook syncing, activity matching); should be a clearly separated future phase, not v1.

**Next step:** confirm the two defaults above (manual renewal + self-reported results), then start implementation with Phase 1 (`product_running_specs`) since it's the shared dependency for the shoe finder and better club event targeting.
