## Phase 2 — Audit findings (tracked in `docs/todolist.md`)

A background agent compared the live PHP site against `src/app/` and returned 7 findings, prioritized by impact. All were actioned; #5 was declared not applicable to this site.

### 1. `login.php` — auth system was a fraction of `LoginPage.tsx`

**Problem:** only phone+password login and direct phone registration existed. No password recovery at all — a real customer who forgot their password had no way back in. Also missing: OTP-based login/registration, email login/registration, Google/Facebook social login, and settings-based gating of which methods are even offered.

**Fix:** rewrote `login.php` as a full client-side state machine mirroring `LoginPage.tsx`'s ~13-step flow — phone and email, each with password and OTP paths; forgot-password for both; direct (no-OTP) and OTP-verified registration with a choose-step when both are enabled; Google/Facebook social login with phone-linking for first-time social users. Every path is gated by the real admin settings (`login_phone_password_enabled`, `login_phone_otp_enabled`, `login_register_without_otp_enabled`, `login_email_enabled`, `register_email_enabled`, `login_google_enabled`, `login_facebook_enabled`), matching `LoginPage.tsx`'s settings-derivation logic exactly (including that `login_email_password_enabled`/`login_email_otp_enabled` are aliases of the same `login_email_enabled` key, not separate settings).

Verified live against the site's actual current settings: direct phone registration → auto-login → redirect, phone password login, and the forgot-password flow correctly reporting "unavailable, contact support" when OTP is admin-disabled (rather than silently offering no path, which was the original bug).

### 2. Bulk/volume price tiers not applied

**Problem:** `product_price_tiers` existed in the schema and was already used by `backend/api/orders.php` at order-creation time, but neither `product.php` (display) nor `cart-action.php` (cart pricing) applied it — customers saw and paid the base price regardless of quantity.

**Fix:**
- `cart-action.php` now computes the tiered unit price (highest `min_qty` tier ≤ qty) on add, on merge into an existing cart line (recomputed against the *combined* qty, so a second "add" can correctly cross a threshold), and on quantity update. Tiers only apply to products without variants, matching `getEffectivePrice()` in the React reference.
- `product.php` fetches `product_price_tiers`, renders a "Олноор авбал хямд" bulk-discount table, and live-updates the displayed price/active tier row as quantity changes.

**Bug found along the way:** the product page's price-display JS selector (`.tf-product-info-price .price-new`) didn't match the actual markup (`.product-info-price`) — live price updates on variant/quantity change had been silently broken even before this fix.

### 3. No per-shop landing pages

**Problem:** `shop.php`'s sidebar "Брэнд" checkbox only *filters* the generic product grid — it's not a dedicated shop page. `/shop/{slug}` looked like it worked (returned HTTP 200) but was actually a silent no-op: no `.htaccess` rule existed for it, so the request fell through via the same `PATH_INFO`-leak mechanism that caused the earlier blog.php bug (Apache resolves `/shop` to `shop.php` and hands `/{slug}` off as `PATH_INFO`, which `shop.php` never read) — landing on the unfiltered generic page instead of a shop-specific one. Homepage was also missing the shops grid section `HomePage.tsx` has.

**Fix:**
- Added a real `.htaccess` rule: `^shop/([^/]+)/?$` → `shop.php?shop_slug=$1`.
- `shop.php` gained a landing-page mode: resolves the slug against `shops` (404s on unknown/inactive), scopes the product query to that shop, shows a hero banner (logo, name, description, product count, tinted with the shop's own `color` field via a new shared `hexToLight()` helper in `includes/config.php` — matches `ShopPage.tsx`'s hero styling), hides the now-redundant brand sidebar filter, and rewrites all filter/sort/pagination URLs to stay under `/shop/{slug}`.
- Homepage (`index.php`) now has the shops grid section (`shops_title`/`shops_description` settings-driven heading, color-tinted cards linking to the new landing pages) matching `HomePage.tsx`'s "Trust Section".
- Bonus (requested mid-session): added a "Брэнд" pill row to the header mega-menu linking to each shop's landing page. The existing 4-column mega-menu grid (Хүйс/Ангилал/Спортын төрөл/gender images) was already at Bootstrap's 12-column limit, so this is a horizontal row below the grid rather than a 5th column.

### 4. No sort / new-arrivals filter

**Problem:** `shop.php` and `category.php` had no way to sort results or filter to only new arrivals, unlike `ShopPage.tsx`.

**Fix:** added a "Эрэмбэлэх" sort dropdown — design lifted from `ochaka/shop-default.html`'s `.tf-dropdown-sort` — with Шинэ/Алдартай/Үнэ↑/Үнэ↓ options matching `ShopPage.tsx`'s `sortMap`, plus a "✨ Зөвхөн шинэ бараа" new-arrivals filter (products created in the last 30 days, matching `backend/api/products.php`'s `new` param). Wired into both `shop.php`'s checkbox-form filters and `category.php`'s link-based filters, preserved across pagination/category/search URLs.

**Bug found along the way:** the `shop-default.html` demo markup puts `data-bs-toggle="dropdown"` on the *outer* `.tf-dropdown-sort` wrapper, which also contains the option links — Bootstrap's toggle click-handler was intercepting and calling `preventDefault()` on every click bubbling up from inside it, silently blocking navigation (the demo never hit this since its options were inert `<div>`s, not real links). Fixed by moving `data-bs-toggle="dropdown"` to the inner `.btn-select` trigger.

### 6. Contact form doesn't send anything

**Problem:** `contact.php`'s form was entirely fake — the JS just faked a success message via `setTimeout`, never actually sending or storing anything.

**Fix** (no React source of truth here — `ContactPage.tsx` has no form at all, just static info cards — so this was built to match existing site conventions):
- **Migration** `061_contact_messages` (`backend/migrate.php`) — new table, applied via the normal migration runner.
- **API** `backend/api/contact.php` — validates fields, then layers spam defenses: a hidden honeypot field (silently faked as success, never stored — no signal given to spammers), a submit-timestamp time-trap (rejects <2s from page-load as spam; a *missing* timestamp is treated the same way since only a raw bot POST would omit what real browser JS always sends), a link-stuffing/markup content heuristic, and dual rate-limiting (session-based, matching `check-phone.php`'s existing pattern, plus a DB IP-based check that survives a cleared session cookie) capped at 5/hour. Spam-flagged messages are still stored (`status = spam`) for admin review rather than silently dropped.
- **Admin module** `backend/pages/contact-messages.php` (+ router/sidebar registration, `super_admin`-only like `testimonials`/`sliders`) — status-filtered list (Шинэ/Уншсан/Спам) with mark-read/mark-spam/restore/delete actions.
- `contact.php`'s form now really POSTs to the endpoint instead of faking success.

**Bug found along the way:** the endpoint originally sent a best-effort admin-notification email synchronously via the existing `sendEmail()` SMTP helper, but a slow/unreachable mail host made visitors wait 4+ seconds for a response (the SMTP handshake's multi-step nature meant per-step timeout tuning didn't help — the stall was network-level, before any single step's timeout could fire). Since email notifications weren't actually requested and the admin panel is the real notification path, removed the synchronous email call entirely rather than chase a fragile async workaround. Response time dropped to a consistent ~150ms.

### 7. Cart doesn't show cargo fee

**Problem:** `cart.php` never displayed the preorder cargo/shipping fee.

**Fix:** computed using the real per-batch cargo model — not `CartPage.tsx`'s simplified flat `cargo_rate_per_kg` setting, which the backend has since superseded with per-batch rates. Each preorder item's `cargo_batch_id` is looked up against that batch's own `cargo_rate_per_kg` (only `status = 'open'` batches count), mirroring `backend/api/orders.php`'s authoritative `weight_kg * rate * qty` calculation exactly. Shows a per-item "+ ачааны X₮" note (or "Ачаа ирэхэд төлнө" for `hide_cargo_fee` items, excluded from the total and shown as a footnote instead — matching `CartPage.tsx`'s `hasCargoItems`/`hideCargoFee` split), a summary "Ачааны төлбөр" row, and folds it into the grand total.

**Two pre-existing bugs found along the way**, both from `cart.php` reusing Ochaka theme demo class names that collide with generic handlers in `ochaka/js/main.js`:
1. `.minus-quantity`/`.plus-quantity` were double-bound — main.js's `deleteFile()` delegates its own +/- handler off `.each-prd`/`.list-file-delete` ancestors, firing alongside cart.php's own fetch-backed handler and incrementing/decrementing quantity by 2 instead of 1. (Same root cause as a separate bug found and fixed on `product.php`'s own quantity buttons, but needed a different fix here — see below.)
2. `.each-price`/`.each-subtotal-price`/`.each-total-price`/`.each-list-prd` were also theme hooks — main.js's `updateTotalPriceEach()` was silently overwriting the grand total with a cargo-blind recalculation. Fixed by renaming all of them to cart.php-owned class names.

Also had `cart-action.php`'s `update` action return the tier-recomputed unit price (finding #2), since cart.php's quantity-change JS was reading a stale `data-price` after a bulk-tier threshold was crossed via the cart page itself.

## Related bug: product page quantity buttons incrementing by 2

Found independently (user-reported) while working the audit list. `ochaka/js/main.js`'s `totalPriceVariant()` binds its own +/- click handler to `.btn-increase`/`.btn-decrease` inside `.tf-product-info-list` — the exact container `product.php` uses for its own (separately fetch-backed) handler. Every click fired both. Fixed with `event.stopImmediatePropagation()` inside `product.php`'s handler (which registers first, at page-parse time, before main.js's DOMContentLoaded-bound listener) — this blocks main.js's later-registered listener on the same element from firing.

Note this is a *different* fix from the cart.php version of the same bug class: there, main.js's handler is structurally positioned to fire *before* cart.php's own (it's a delegated listener on an ancestor element, not a direct listener on the same node), so `stopImmediatePropagation()` wouldn't have worked — removing the colliding `.each-prd` class was the correct fix instead.

## Cross-cutting notes

- **Theme class-name collisions** turned out to be a recurring bug source: Ochaka's `main.js` binds generic handlers by class name (`.each-prd`, `.minus-quantity`, `.each-total-price`, etc.) rather than by page-specific scoping, so any PHP page reusing those class names for its own unrelated JS silently inherits main.js's behavior too. Worth checking for this pattern before reusing theme classes on new pages.
- **`PATH_INFO` leaks** are a repeat root cause (blog.php earlier, `/shop/{slug}` this session) — any clean-URL route without an explicit `.htaccess` rule can silently resolve to the base `.php` file with the extra path segment ignored, producing a "soft 404" (200 status, wrong content) rather than a real one.
- All fixes were verified live via Playwright (browser automation) and/or direct `curl`/PDO checks against the real dev DB, with disposable test data (products, cart sessions, contact messages, admin sessions) cleaned up afterward in every case.
