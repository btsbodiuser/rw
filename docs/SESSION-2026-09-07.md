Continuation of the storefront work started in [SESSION-2026-09-06.md](SESSION-2026-09-06.md).

duplicated markup that a small change (like removing a topbar switcher) had

## 2. Header + footer extracted to shared partials

### The problem

Ten storefront pages (brands, index, shop, product, cart, login, signup,
account, plus the two new contact + track-order) each carried a full copy of
the header wrapper (topbar + main nav + mobile nav + burger + search modal +
categories offcanvas + cart offcanvas — ~2,832 lines) *and* the footer
wrapper (welcome-banner modal + quickview modal + popup cart modal + coupon
modal + comparison drawer + `<footer>` + copyright + all vendor scripts —
~5,893 lines). That's **~92,000 lines total** across ten files, most of it
identical. The topbar switcher removal had to be applied to 10 files as a
single regex sweep; that was the tell.

### The fix

Extracted the shared blocks into [`includes/header.php`](../includes/header.php)
and [`includes/footer.php`](../includes/footer.php), then rewrote each root
page as a thin PHP prep + main content + require calls.

- **Verified before extracting**: sliced the header/footer regions out of
  every page and diffed them against `brands.php` (canonical for header) and
  `index.php` (canonical for footer). Diffs were CSS-only in the `<style>`
  block for headers, and 0-line for footers except `shop.php` which had a
  legit page-scoped mobile-filter-drawer script that had been copy-pasted
  into 7 other pages where it did nothing. That script moved to `shop.php`'s
  `$extraScripts`.
- **`includes/header.php`** fetches its own nav data (categories, shoe
  types, run types, gait types, technical features, popular brands) so
  pages don't have to prepare it. Reads `$page_title` (required),
  `$extraStyles` (optional page CSS), `$bodyClass` (optional).
- **`includes/footer.php`** reads optional `$extraScripts` and injects them
  right before `</body>`.
- **`includes/config.php`** absorbed shared helpers that pages used before
  requiring the header: `h()`, `navShopUrl()`, `navGenderUrl()`,
  `renderProductCard()` (previously defined identically in all 8 pages),
  plus the shared page globals `$urlHome/$urlShop/$urlCart/$urlAccount/
  $urlLogin/$urlLogout/$loggedIn/$sessionUser` (defined *after* the
  remember-me bootstrap so they reflect a restored session).

## 5. Newsletter subscribe made dynamic + wired to API

Two hardcoded English newsletter surfaces in the footer:
- Blue strip above footer: "Subscribe our newsletter / Subscribe and get
  discount 20% Off"
- Welcome-banner popup modal: "Don't miss out Offers / Be the first one…"

The backend endpoint [`backend/api/subscribe.php`](../backend/api/subscribe.php)
was already fully built (IP rate limit, idempotent upsert on email,
reactivate-if-inactive path, Mongolian success/error messages) — just had
nothing calling it.

**Migration 071** seeded 11 settings for the two surfaces:
- Footer strip (5): `newsletter_footer_enabled` (bool, on),
  `newsletter_footer_title/subtitle/placeholder/btn` — all Mongolian defaults
- Popup modal (6): `newsletter_modal_enabled` (bool, **off** — opt-in),
  `newsletter_modal_title/subtitle/placeholder/btn/skip`

**Migration 072** added popup show-behaviour:
- `newsletter_modal_delay_ms` (default 6000)
- `newsletter_modal_cooldown_days` (default 7)

**Wiring** in `includes/footer.php`:
- Both forms have `class="rw-newsletter-form"` + `data-newsletter-form="footer|modal"`
  and a sibling `.rw-newsletter-status` div
- One shared submit handler (JS) fires JSON POST to `/backend/api/subscribe.php`,
  clears input on success, renders status pill inline
- Whole modal DOM only renders when `newsletter_modal_enabled` is on
- Whole footer strip hidden when `newsletter_footer_enabled` is off

**Popup auto-trigger** — schedules `bootstrap.Modal.getOrCreateInstance(el).show()`
after `newsletter_modal_delay_ms`. Records `localStorage['rw_newsletter_seen_at']`
on `hidden.bs.modal`, so subsequent visits within the cooldown window skip
the show. Manual trigger for testing:
```js
bootstrap.Modal.getOrCreateInstance('#welcomebannerModal').show()
```

**Status pill polish** (three follow-up fixes):
1. Empty status was reserving 18px of dead space — dropped `min-height`,
   used `:not(:empty)` so the pill's margin only applies when populated
2. Green/red text on the blue footer strip was low-contrast — switched to a
   white pill with coloured text + coloured border so it reads on any bg
   (blue footer, white modal)
3. Messages stuck around indefinitely — added `setStatus()` / `clearStatus()`
   helpers with a per-element `WeakMap` of timers; message renders,
   fades opacity at 4 s, DOM cleared at 4.4 s. Timers cancelled if the user
   submits again mid-hide

## 8. Bugs found and fixed

### 8.1 signup OTP: SSL cert failure on WampServer

Symptom: signup phone-OTP send returned "СМС илгээх үед алдаа гарлаа. Дахин
оролдоно уу." — but the backend orders page's SMS send worked fine.

Root cause: **code duplication drift**. `backend/api/auth/send-otp.php` had
a hand-rolled cURL block with `CURLOPT_SSL_VERIFYPEER => true`; the working
helper [`sendSingleSMS()`](../backend/includes/functions.php#L946) in the
backend uses `CURLOPT_SSL_VERIFYPEER => false`. WampServer's PHP has no CA
bundle configured, so verification fails and no request goes out.

Fix wasn't just to flip the flag — that leaves two SMS-send paths that will
drift again. Rewrote `send-otp.php` to call `sendSingleSMS()`. One code
path, one behavior, one place to fix cert / rate-limit / retry logic in
the future.

**Diagnostic scaffolding added along the way** (kept): if `sendSingleSMS()`
fails, the response now includes a `debug.reason` field so the failure
mode is visible in DevTools instead of hidden behind a generic message.

### 8.2 OTP rate-limit hit during dev testing

Debug retries burnt through the 5-per-hour-per-phone limit in
`send-otp.php` (lines 32-39). Cleared with a targeted DELETE:
```sql
DELETE FROM otp_codes
WHERE phone = ? AND code <> 'login_fail'
  AND created_at > DATE_SUB(NOW(), INTERVAL 1 HOUR)
```
(the `code <> 'login_fail'` clause keeps the login-attempt rate-limit
history intact — those rows also live in `otp_codes`).

For future iteration: admin can flip `login_register_without_otp_enabled`
to `1` in settings, which routes signup through
[`register-direct.php`](../backend/api/auth/register-direct.php) (phone +
password, no SMS burnt while iterating on the UI).
