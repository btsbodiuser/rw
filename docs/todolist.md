# Audit Findings — PHP site vs React reference (src/app/)

Findings from comparing the live PHP site against `src/app/` (the working React reference), prioritized by impact.

- [x] **1. login.php auth system incomplete** — was missing OTP-based login/registration, password-recovery/forgot-password flow (real customers had NO way to recover a forgotten password), email login/registration, Google/Facebook social login, and settings-based gating of which methods are offered.
  - Fixed: rewrote `login.php` as a full state machine matching `LoginPage.tsx` (phone + email, password + OTP, forgot-password, direct/OTP registration, social login), all gated by admin settings. Verified live via Playwright.

- [x] **2. Bulk/volume price tiers not applied** — `product.php` + `cart-action.php` don't apply quantity-based volume pricing that the React reference supports.
  - Fixed: `cart-action.php` now computes the tiered unit price (highest `min_qty` tier ≤ qty, sorted ASC, mirroring `backend/api/orders.php`'s `effectiveTierPrice()`) on add, on merge into an existing cart line (recomputed against the *combined* qty), and on quantity update — tiers only apply to products without variants, matching `getEffectivePrice()` in the React reference. `product.php` now fetches `product_price_tiers`, renders a "Олноор авбал хямд" tier table, and live-updates the displayed price/active tier row as quantity changes.
  - Also fixed a pre-existing bug found along the way: the product page's price-display selector (`.tf-product-info-price .price-new`) didn't match the actual markup (`.product-info-price`), so live price updates on variant/quantity change were silently broken even before this fix.
  - Verified: tier rows render correctly, live price/active-row updates on qty change, and cart pricing (add / merge-crossing-threshold / update) all recompute correctly — checked via direct API calls and Playwright.

- [x] **3. No per-shop landing pages** — `/shop/{slug}` 404s; homepage is missing the shops grid section present in the React reference.
  - The confirmed gap: `shop.php`'s existing sidebar "Брэнд" checkbox only *filters* the generic product grid — it doesn't give shops their own page. `/shop/{slug}` wasn't actually 404ing (returned 200) but was a silent no-op: no `.htaccess` rule existed for it, so it fell through via the same `PATH_INFO`-leak mechanism as the earlier `blog.php` bug (Apache resolves `/shop` to `shop.php` and hands `/{slug}` off as `PATH_INFO`, which `shop.php` never read) — landing on the *unfiltered* generic page instead of a shop-specific one.
  - Fixed:
    - Added a real `.htaccess` rule (`^shop/([^/]+)/?$` → `shop.php?shop_slug=$1`).
    - `shop.php` now has a landing-page mode: resolves the slug against `shops` (404s on an inactive/unknown one), forces the product query to that shop, shows a hero banner (logo, name, description, product count, tinted with the shop's own `color` field via a shared `hexToLight()` helper — matches `ShopPage.tsx`'s `hexToLight(shopInfo.hexColor)` hero exactly), hides the now-redundant brand sidebar filter, and rewrites all filter/sort/pagination URLs to stay under `/shop/{slug}` instead of falling back to the generic `/shop.php`.
    - Homepage now has the shops grid `HomePage.tsx`'s "Trust Section" reference has (`shops_title`/`shops_description` settings-driven heading, color-tinted cards per shop linking to their new landing page) — this was missing entirely before.
    - Bonus (user request): added a "Брэнд" pill row to the header mega-menu, linking each shop to its landing page. The existing 4-column mega-menu grid (Хүйс/Ангилал/Спортын төрөл/gender images) was already at its 12-column limit, so this is a horizontal row below the grid rather than a 5th column, avoiding a layout rework.
  - Verified live via Playwright + direct requests: `/shop/outlet` shows the correct hero/product count (matches DB exactly) and 404s for an unknown slug; sort/gender-filter changes stay under `/shop/outlet` instead of reverting to `/shop.php`; the brand sidebar filter is confirmed absent (not just a text-match false positive — checked for the actual `#sidebar-shops` block); homepage grid and mega-menu pills both render correct links and navigate correctly with no console errors.

- [x] **4. No sort / new-arrivals filter** — `shop.php` and `category.php` lack the sort/new-arrivals filtering the React reference has.
  - Fixed: added a "Эрэмбэлэх" sort dropdown (design from `ochaka/shop-default.html`'s `.tf-dropdown-sort`) with Шинэ/Алдартай/Үнэ↑/Үнэ↓ options matching `ShopPage.tsx`'s `sortMap`, plus a "✨ Зөвхөн шинэ бараа" new-arrivals filter (products created in the last 30 days, matching `backend/api/products.php`'s `new` param) — both wired into `shop.php`'s checkbox-form filters and `category.php`'s link-based filters, and preserved across pagination/category/search URLs.
  - Found and fixed a Bootstrap dropdown bug along the way: `shop-default.html`'s demo markup puts `data-bs-toggle="dropdown"` on the *outer* `.tf-dropdown-sort` wrapper, which also contains the option links — Bootstrap's toggle click-handler was intercepting and `preventDefault()`-ing every click bubbling up from inside it, silently blocking navigation (the demo never hit this since its options were inert `<div>`s, not real links). Fixed by moving `data-bs-toggle="dropdown"` to the inner `.btn-select` trigger, whose sibling `.dropdown-menu` Bootstrap still resolves correctly.
  - Verified live via Playwright: price_asc/price_desc actually reorder results, new-only filter narrows the result count, and both fixes apply to shop.php and category.php identically. No console errors.

- [x] **5. Seller "add product" page missing** — `product-entry.php` doesn't exist at all.
  - Not needed for this site (user decision) — no seller/multi-vendor workflow applies here.

- [x] **6. Contact form doesn't send anything** — `contact.php`'s form has no backend endpoint to actually deliver the message.
  - Fixed. `src/app/pages/ContactPage.tsx` has no form at all (just static info cards), so there was no React contract to mirror here — built to match the existing site conventions instead:
    - **Migration** `061_contact_messages` (`backend/migrate.php`) — new `contact_messages` table (name/email/phone/message/ip/user_agent/status, indexed on status and on ip+created_at for rate-limiting), applied via the normal migration runner.
    - **API** `backend/api/contact.php` — validates fields, then layers spam defenses: a hidden honeypot field (bots fill every field; real users never see it — silently faked as success, never stored, so spammers get no signal), a submit-timestamp time-trap (rejects <2s from page-load as spam, and treats a *missing* timestamp the same way since only a raw bot POST would omit what real browser JS always sends), a link-stuffing/markup content heuristic, and dual rate-limiting (session-based, matching `check-phone.php`'s existing pattern, plus a DB IP-based check that survives a cleared session cookie) capped at 5/hour. Spam-flagged messages are still stored (status `spam`) for admin review rather than silently dropped, except honeypot hits.
    - **Admin module** `backend/pages/contact-messages.php` (+ router/sidebar registration, `super_admin`-only like `testimonials`/`sliders`) — status-filtered list (Шинэ/Уншсан/Спам) with mark-read/mark-spam/restore/delete actions, matching the existing CSRF + `hasRole()` conventions.
    - `contact.php`'s form now really POSTs to the endpoint (with the honeypot field and a client-set `rendered_at` timestamp) instead of faking success via `setTimeout`.
  - Also found and fixed a real bug while testing: the endpoint originally sent a best-effort admin-notification email synchronously via the existing `sendEmail()` SMTP helper, but a slow/unreachable mail host made visitors wait 4+ seconds (SMTP's multi-step handshake made per-step timeout tuning ineffective — the stall showed up before any single step's timeout could fire). Since the user didn't ask for email notifications and the admin panel is the real notification path, removed the synchronous email call entirely rather than chase a fragile async workaround — response is now consistently ~150ms.
  - Verified live via Playwright + direct API calls: legit delayed submission succeeds and stores as `new`; instant/no-timestamp submissions are flagged `spam` but still show success to the user; link-stuffed messages are flagged `spam`; honeypot submissions fake success and are never inserted; rate limiting 429s correctly after 5/hour (confirmed by exhausting my own test quota); admin page lists, filters, and mark-read/mark-spam/delete all work. All test data cleared, temporary test admin session destroyed (no admin credentials were touched).

- [x] **7. Cart doesn't show cargo fee** — `cart.php` doesn't display the delivery/cargo fee shown in the React reference's cart.
  - Fixed using the real per-batch cargo model (not `CartPage.tsx`'s simplified flat `cargo_rate_per_kg` setting, which the backend has since superseded): `cart.php` now looks up each preorder item's `cargo_batch_id` → the batch's own `cargo_rate_per_kg` (only counting `status='open'` batches), mirroring `backend/api/orders.php`'s authoritative `weight_kg * rate * qty` calculation exactly, since that's what actually gets charged at order time. Shows a per-item "+ ачааны X₮" note (or "Ачаа ирэхэд төлнө" for `hide_cargo_fee` items, excluded from the total and shown as a footnote instead, matching `CartPage.tsx`'s `hasCargoItems`/`hideCargoFee` split), a summary "Ачааны төлбөр" row, and folds it into the grand total.
  - Found and fixed two pre-existing bugs surfaced while wiring this up, both from `cart.php` reusing Ochaka theme demo class names that collide with generic handlers in `ochaka/js/main.js`: (1) `.minus-quantity`/`.plus-quantity` were double-bound — main.js's `deleteFile()` delegates its own +/- handler off `.each-prd`/`.list-file-delete` ancestors, firing alongside cart.php's own fetch-backed handler and incrementing/decrementing quantity by 2 instead of 1 (same root cause as the earlier product.php quantity-button bug, different fix needed since main.js's handler here sits structurally *before* cart.php's in bubble order — removing the colliding `.each-prd` class was the fix, not `stopImmediatePropagation()`); (2) `.each-price`/`.each-subtotal-price`/`.each-total-price`/`.each-list-prd` were also theme hooks — main.js's `updateTotalPriceEach()` was silently overwriting the grand total with a cargo-blind recalculation (and, combined with the `.each-prd` removal, briefly zeroed it out entirely since its selector then matched nothing). Renamed all of them to cart.php-owned class names so its own JS is the sole source of truth.
  - Also had `cart-action.php`'s `update` action return the tier-recomputed unit price (finding #2) in its response, since cart.php's quantity-change JS was reading a stale `data-price` after a tier threshold was crossed via the cart page itself — a latent bug from the earlier fix, caught here because it fed directly into this total's correctness.
  - Verified live via Playwright with a temporary test preorder product (weight + open cargo batch): correct fee at initial load, correct live rescaling through +/- clicks (single-step, no double-count), correct exclusion/footnote behavior for `hide_cargo_fee`, and no regression for non-cargo items. All test data reverted.
